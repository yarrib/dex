# PRD: dex.lock — Reproducible Trait & Skill Resolution

**Status:** Future / Not Started
**Target:** TBD (post-v0.3)
**Owner:** TBD

---

## Problem

`dex.toml` records user intent — which traits and skill packs a project wants.
When those sources are remote (git repos with mutable refs like `main`), there
is no guarantee that `dex add` or `dex skills sync` resolves the same files
across machines or over time. A developer on one machine may get a different
version of a trait or skill than CI, or than a colleague running `dex skills sync`
a week later.

This is the same problem `Cargo.lock` and `uv.lock` solve for package managers.

---

## Non-Problem (Today)

Currently all traits and built-in skill packs are **embedded in the binary** at
compile time. There are no external versions to drift. `dex.lock` would add no
value today and is explicitly out of scope until remote trait/skill sources are
first-class.

---

## Proposed Solution

Introduce `dex.lock` — a machine-generated, committed lockfile that records the
exact resolved state of all remote trait and skill sources.

### What gets locked

| Source type | Locked fields |
|---|---|
| Remote trait repo (`url` + `ref`) | resolved git commit SHA |
| Remote skill pack repo (`url` + `ref`) | resolved git commit SHA |
| Built-in (embedded) | not locked — binary version is the pin |

### File format

```toml
# dex.lock — generated by dex. Do not edit by hand.
# Commit this file to ensure reproducible dex add / dex skills sync.

[[trait]]
name    = "ci-github"
source  = "https://github.com/my-org/dex-traits"
ref     = "main"
commit  = "a1b2c3d4e5f6..."

[[skill]]
pack    = "databricks"
source  = "https://github.com/databricks-solutions/ai-dev-kit"
ref     = "main"
commit  = "f6e5d4c3b2a1..."
```

### Commands that write dex.lock

| Command | Behavior |
|---|---|
| `dex add <trait>` | resolves + locks the trait source |
| `dex skills sync` | resolves + locks all skill sources |
| `dex lock update` | re-resolves all sources to latest, updates lock |
| `dex lock update <name>` | re-resolves a single source |

### Commands that read dex.lock

| Command | Behavior |
|---|---|
| `dex add <trait>` | if lock exists for source, uses pinned commit (no drift) |
| `dex skills sync` | if lock exists, checks out pinned commit from cache |
| `dex lock check` | exits non-zero if lock is out of sync with dex.toml |

### CI usage

```yaml
- run: dex lock check   # fail if dex.lock is stale
- run: dex skills sync  # installs from pinned commits in dex.lock
```

---

## Design Decisions

**Should `dex.lock` be committed?**
Yes — same reasoning as `Cargo.lock` for binaries/applications. It ensures every
contributor and CI run gets the same traits and skills.

**What about embedded (built-in) traits/skills?**
Not locked — the binary version acts as the implicit pin. If a user upgrades dex,
built-in traits may change, which is intentional.

**Should `dex.toml` reference versions?**
No. `dex.toml` stays intent-only (like `pyproject.toml`). Version pinning is
exclusively `dex.lock`'s job.

**What if dex.lock doesn't exist?**
Behave as today — resolve from remote and warn that no lockfile exists. Do not
error, to keep the upgrade path smooth.

---

## Prerequisites

- Remote trait sources (`[traits.remotes]` in `dex.toml` or user config) — not yet implemented
- Remote skill pack sources are partially implemented (`dex skills add <url>`)
- `dex lock` subcommand group

---

## Out of Scope

- Locking built-in (embedded) traits or skills
- Checksums / content hashing (git commit SHA is sufficient)
- Dependency resolution between traits (traits are independent)
