Project Memory — User Manual

A linked knowledge graph of every architecturally significant decision, feature, and fix in dex. It lives in .context/wiki/ and is generated by the Rust engine dex context sync — and refreshable on demand by the /project-memory-engine skill.

What is this?

.context/wiki/ is a Project Evolution Knowledge Graph. Each Markdown file is one node — a commit that materially shaped the codebase. Nodes connect with Obsidian-style [wikilinks](wikilinks.md) expressing five edge types:

EdgeMeaning
[influenced-by](influenced-by.md)Builds on a prior decision
[modified-by](modified-by.md)Alters a design pattern (usually a bug fix)
[implemented-in](implemented-in.md)Connects a design doc to the code that realises it
[co-occurrence](co-occurrence.md)Files that consistently change together (coupling)
resolved-byConnects an Issue / PR ID to the resulting change

Nodes are labelled by type: [Decision] architectural pivot · [Evolution] major feature · [Stability] bug fix or hardening · [Dependency] environment / config / packaging.

The entry point is .context/wiki/INDEX.md — a “city map” of nodes grouped by functional area (Foundation, Template Engine, Scaffolding, CLI, Skills & Traits, MCP & AI, Templates, Docs/CI/Release).

For three audiences

1. Human stakeholders — “Was the work well spent?”

Point leadership and reviewers at two places:

  • .context/wiki/INDEX.md — the Knowledge Map view. Functional areas, each with the commits that moved the needle. Reads like a table of contents.
  • .context/wiki/<sha>-*.md — the Traceability view. Every node names the commit SHA, author, date, the [Decision | Evolution | Stability | Dependency] class, and the files it touched.

Together they show that architecture was intentional, not accidental drift — click from an area straight to the commit that introduced a change, and from there to the design decision that justified it.

2. Technical team — “How do I actually use this?”

The graph is plain Markdown with [wikilinks](wikilinks.md), so it renders as a real graph in any of these:

  • Obsidian — open dex/ as a vault, then Graph View (⌘G). Filter by tag (#decision, #stability, …) to see different slices.
  • Logseq — open the repo root; wikilinks become live page refs with backlinks.
  • VS Code — install Foam or Markdown Links for hover-preview and graph panels.

Typical workflows:

  • “Why does the template engine look like this?” → open its most recent node, follow [influenced-by](influenced-by.md) upward.
  • “What breaks if I touch scaffold.rs?” → search the wiki for scaffold.rs in [co-occurrence](co-occurrence.md) clusters; the coupled files surface immediately.
  • “Who introduced the trait system?” → find the [Decision] node in Skills, Traits & Extensibility and read its rationale.

Rule of thumb: before you change a module, open its node first. If you’re about to violate a [co-occurrence](co-occurrence.md) cluster, you’ve taken on extra surface.

3. AI agents — the most important part

The graph’s real value is that a fresh agent can inherit the project’s accumulated judgment the moment it opens the repo. Two mechanisms do this:

  1. CLAUDE.md / AGENTS.md at the repo root — auto-loaded every session. Their Architectural History section points to .context/wiki/INDEX.md.
  2. The /project-memory-engine skill — regenerates the graph and can enrich it.

To bootstrap a new session, prompts like these become powerful:

  • “Before you change anything, read .context/wiki/INDEX.md and tell me which nodes are relevant.”
  • “Why did we choose minijinja for templating?” — the agent finds the relevant [Decision] node and answers from captured rationale, not guesswork.
  • “Add a new subcommand. What else has to change?” — the agent follows [co-occurrence](co-occurrence.md) to surface the files that always move together.

Without the graph, every session starts from zero. With it, your AI “inherits” every design call you’ve documented — a transferable memory across people, IDEs, and model versions.

Refreshing the graph

Two ways, same output directory:

  • Rust engine (deterministic): dex context sync
    • Incremental — only commits newer than what’s already on disk get new nodes.
    • dex context sync --rebuild regenerates every node from scratch.
    • dex context sync --limit N caps history to the most recent N commits.
  • Skill (deterministic + semantic): say “sync project memory”, “rebuild wiki”, or run /project-memory-engine. The skill runs the engine, then can refine classifications and add semantic edges that heuristics miss. It leaves the door open for local-LM assist later.

Cadence we recommend:

  • Run it at the end of every milestone so reports pull from a fresh graph.
  • Run it whenever a [Decision]-class change lands so future sessions pick it up.

To force a full rebuild, run dex context sync --rebuild.

FAQ

Will .context/wiki/ be auto-scanned on every prompt? No. Only CLAUDE.md is auto-loaded. The graph is consulted on demand — an agent reads it when relevant or when a prompt points there. The one-line pointer in CLAUDE.md is usually enough.

What about secrets? Nodes summarise commits — they don’t copy code. Still, review a node before sharing externally; a commit message can leak issue IDs.

Can I hand-edit a node? Yes. The engine is incremental and won’t overwrite existing node files (only --rebuild does). Add domain context freely — that insight then flows to every future AI session.

What if a node becomes wrong? Edit or delete the file. The engine won’t resurrect it unless its SHA appears as a new commit (which it won’t — SHAs are immutable). INDEX.md is regenerated each run.
